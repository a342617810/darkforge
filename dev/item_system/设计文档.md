# 装备生成与词条系统：重构设计

整理于 2026-10-26。起因：想做到暗黑 3 那种词条（列表见第 3 节），现有词条系统做不到。

目前阶段：**最小验证（第 7 节）已通过；阶段 1「迁移」（第 8 节）设计已定，准备开工**。词条的去留和合并见同目录的 `词条一览.md`。
流派（bd）和机制词条的设计单独写在同目录的 `bd设计.md`（逐条词条表 `bd词条提案.xlsx`）。

相关代码：重随 `launcher\reroll\`（`regen.py`、`rr\equipment.py`、`rr\weapons.py`、`rr\container.py`），DLL `dev\rng_*`。

---

## 1. 现在的系统

### 1.1 装备怎么来的

- RNG Lands 包里的装备是**固定编号的成品**：每件一行参数、一条名字和说明。现在的 regulation 里武器表有 1.4 万多行。
- 每次启动重随（`regen.py`）会把**没拥有的** RNG 装备重新组装：
  - 防具：本体照同部位、同稀有度的一件整行复制，再换 1~3 个词条；
  - 护符：照同稀有度的一件护符复制；
  - 武器：本体、补正包、战技分别取自 3 把同类型、同稀有度的武器。
- **已拥有的**按配方 / 快照冻结。配方存在 `%APPDATA%\EldenRing\DarkReforged_item_state.json`，玩家手里的东西因此不变。
- 怪物掉落是按地区档位的大表，每档约 3000 种装备。

### 1.2 词条是什么

- 词条 = RNG Lands 包里现成的特殊效果（SpEffect），一共约 200 种。防具挂在常驻效果格（3 格），护符每件一个。
- **同一个词条、同一个稀有度共用一个效果编号**，所以：
  - 数值是固定档，做不到「掉落时随机、之后固定」；
  - 两件同稀有度的同一词条只算一次（同一个效果挂两次只生效一次）。
- 能叠不能叠由效果类别（spCategory）**碰巧**决定，不是设计出来的：0 / 10 叠加，20 互相顶掉，100 以上互斥。
- 武器没有词条位，只有「本体 + 补正包 + 战技」。

### 1.3 运行时（DLL）

都是零散的单个功能：

| DLL | 内容 |
|---|---|
| dark_sell | 一键出售、免费许愿、复制战灰；在内存里改确认框文字 |
| dark_lock | 物品弹出菜单加「锁定」 |
| dark_wings | 熔炉百相之羽飞行 |
| dark_core | 杂项模块：庆典油脂、容器验证 |

没有统一的「词条引擎」。

### 1.4 做不到的根本原因

特殊效果参数只能表达静态加成，以及按动作类型、血量等条件触发的加成、附近触发。它做不到：

- 计时、计数（连击数、喝瓶后若干秒）；
- 读写血量和异常值（按最大血量扣血、结算剩余异常）；
- 改动作（取消、无敌帧、动作速度）；
- 影响别的角色（治疗队友、附近减速）。

---

## 2. 目标

1. 支持第 3 节这一级别的词条，并且**以后还能继续加**：加词条尽量只改数据。
2. **数值在掉落时随机，之后固定。**
3. **掉落装备实时随机生成**，不再靠预先编好大量成品装备。
4. 叠加规则明确写在定义里。
5. 老存档、老装备不坏。

## 4. 总体架构：四层

```
定义层（数据）    data\affixes\*.json：词条定义、生成规则
      │
生成层            掉落 / 鉴定时抽底子、抽词条、抽数值 → 存进这件装备的记录（掉落时固定）
      │
参数层            这件装备自己的参数行 + 自己的效果行（词条数值精确写进去）
      │
逻辑层            玩家动作脚本（动作相关）  +  DLL 词条引擎（伤害、计时、计数、血量、异常、别的角色）
```

### 4.1 定义层

每个词条一条定义：

| 项 | 例子 |
|---|---|
| 键（固定名字，删了也不重复使用） | `giant_slayer` |
| 可出现的部位、武器类型 | 武器；或护符 / 腿甲 |
| 稀有度门槛 | 仅传说 / 仅传说以下 |
| 权重、互斥组 | 同组只能出一个 |
| 数值范围和步长 | 5%~50%，步长 1% |
| 叠加规则 | 取最高 / 相加 / 只算一个 |
| 描述模板（中、英） | 「每次攻击造成目标最大生命值 {v}% 的伤害」 |
| 实现方式 | 参数模板 / 动作脚本 / 引擎积木组合 |
| 强度分 | 给生成时的装备预算用 |

生成规则（如「破坏性超载：3~4 条、数值取最低」）也写成数据。现有约 200 种老词条可以从现有效果自动转成「参数层」词条，继续保留。

### 4.2 生成层

- 抽：底子（本体 / 补正包 / 战技，或防具本体）→ 词条（按部位、稀有度、权重、互斥）→ 数值（按范围、步长）。
- 记录存「词条键 + 抽到的原始数值」，不存效果编号。以后改了数值划分，老装备照样能重算，数值本身不变。
- 分工：重随（Python）准备**零件库**（底子、补正包、战技、词条定义、文字片段），DLL 只按权重拼装。生成逻辑仍然是数据驱动，强度曲线工具（`dev\power_curve`）可以直接读定义。

### 4.3 参数层

- 每件装备有**自己的效果行**，词条数值精确写进去，不再「同稀有度共用一个效果」。
- 能用参数表达的词条，效果行本身就带效果。
- 需要逻辑的词条，效果行只当**标记**，告诉动作脚本和 DLL「身上有这个词条、数值多少」。

### 4.4 逻辑层

- **玩家动作脚本（c0000.hks）**：负责和动作状态有关的（翻滚、跳跃、防御、取消、动画速度）。脚本查玩家身上有没有某个标记效果，再挂效果。我们已经在改这个脚本（不受坠落伤害、蹬墙跳、灵马速度）。
- **DLL 词条引擎（dark_core）**：
  - 三个核心接口：伤害结算钩子（读攻击者、目标、伤害、攻击类型，能改伤害、追加伤害）、每帧计时、事件检测（喝瓶、防御成功、击杀、异常触发）。
  - DLL **按身上装备查词条表**，不靠装备上的效果格。防具只有 3 个常驻效果格，挂在格子上，词条数很快到顶。
  - 需要动作脚本配合的词条，由 DLL 给玩家挂标记效果。
  - 叠加规则统一在 DLL 里算。

## 5. 扩展性

### 5.1 加一个新词条要做什么

| 词条类型 | 例子 | 要做的事 | 改代码吗 |
|---|---|---|---|
| 纯参数 | 强攻、鹰眼视觉、老词条 | 定义里加一条：数值写到哪个字段、范围、描述模板 | 不改 |
| 现有积木的新组合 | 渴血、巨人杀手、血狂、强韧 | 定义里写「触发 + 条件 + 效果」 | 不改 |
| 需要新积木 | 时隙（影响附近敌人）、惊醒（读睡眠状态） | DLL 加一个触发 / 条件 / 效果，之后同类词条都能用 | 改一次 |
| 动作类 | 狼魂、碾压、飞鸿 | 动作脚本里加处理，每类武器动作都要在游戏里验证 | 改，且要逐类测 |

### 5.2 让扩展变便宜的五个设计

1. **DLL 做成积木，不按词条写死**。每个词条拆成「触发 → 条件 → 效果」：
   - 触发：命中、被击中、击杀、防御成功、喝瓶、翻滚、每隔 N 秒、附近出现异常；
   - 条件：连击数、目标有某种异常、自身血量、武器类型；
   - 效果：改伤害倍率、按最大血量追加伤害、回血、加异常积累、挂效果、发射投射物。

   例：巨人杀手 = 命中时，若是第 3 下，按最大血量 5% 追加伤害；渴血 = 附近有人出血时，30 秒内回血 3%。积木攒到二三十个以后，新词条多半只是新组合。
2. **按装备查表，不占装备效果格**：一件装备挂几条词条都行。
3. **编号稳定**：
   - 词条用固定键；
   - 效果编号在预留段里按定义自动分配，分配结果存成锁定文件，中间插新词条也不挪老编号；
   - 记录存原始数值。
4. **版本握手**：
   - DLL 报告自己支持哪些积木，重随遇到不支持的词条就跳过并提示，不会出错崩溃；
   - 游戏更新只补 DLL 地址表，沿用现在 1.17.1 / 1.17.2 两版地址表的做法。
5. **平衡预算**：每个词条带强度分，生成时按总预算抽（类似暗黑 3 的装备预算）。

### 5.3 扩展贵的地方

- **新的触发点**（游戏事件）：每个都要逆向，两个游戏版本各找一次。第一批要把常用触发点做全。
- **动作类词条**：每类武器动作不同，要逐类在游戏里试。
- **影响别的角色**：需要「遍历附近角色」积木，做一次后同类都能用。
- **参数表行数**：每张表最多 65535 行。见 6.5 的估算。

## 6. 实时生成：空白容器 + 运行时填写

### 6.1 为什么不能「凭空造新物品」

- 背包里的装备只是一个编号，所有数值（攻击、补正、模型、图标、词条）都按编号去参数表查。武器查表时去掉强化等级：编号 ÷ 100 × 100。
- 参数表在游戏启动时一次性载入，运行中往里加新行风险很大，因为游戏会记住行的位置。
- 但**改已有行的内容**可以：底层库有改内存参数行的接口（`SoloParamRepository::get_mut`）。

### 6.2 方案

1. **重随只留空行**：参数表里留一批空白行（容器），比如武器 2000、防具 3000、护符 500。这个数是**一个角色同时能持有**的随机装备上限，不是总共能掉多少件。每个容器同时预留几行自己的效果行。
2. **只给占位物品**：掉落表、头目奖励、许愿都改成给占位物品（商店加装备有老问题，要先查清楚），按「部位或武器类型 × 稀有度 × 地区档位」区分。
3. **拿到时填内容**：DLL 选一个空容器，当场生成，写进这一行和它的效果行，再把占位物品换成容器。
4. **按角色记录**：每件的内容记在 `%APPDATA%\EldenRing\` 下，按「存档位 + 角色名」区分。每次读档，DLL 按记录把这个角色的容器全部重写。不同角色共用同一批编号也不冲突，因为同一时间只载入一个角色。
5. **回收**：卖掉或丢弃后，容器回收再用。
6. **文字**：重随在每个容器的名字 / 简介 / 说明里留固定长度的占位，DLL 在内存里找到后原地改写（见 6.4）。

好处：
- 词条数值就是抽到的那个数，不用分档；
- 重随更快、regulation 更小，不用每次启动重组几千件；
- 「掉落时固定」自然成立。

### 6.3 什么时候生成

| 做法 | 体验 | 难度 |
|---|---|---|
| **鉴定**：捡到「未鉴定的传说长剑」，在背包物品菜单里点「鉴定」才生成 | 暗黑 2 风格，多一步操作 | 低。物品菜单加选项 dark_lock 已有；移除物品 dark_sell 已有；只差「往背包加物品」函数 |
| **拾取即生成**：捡起来那一刻就换成成品，弹窗显示成品名字 | 和现在一样，没有额外操作 | 高。要找到「获得物品」函数挂钩，时机早于弹窗 |

建议先做鉴定，跑通后再考虑拾取即生成。

### 6.4 改文字的办法

- **不挂钩取文字函数**：底层库里 MsgRepository 只有空壳，挂钩要逆向。
- 改用**固定长度占位 + 扫内存原地改写**：
  - 重随把占位写成开头带唯一标记、后面补空格到固定长度的字符串；
  - DLL 扫一遍可读写的私有内存（ReadProcessMemory 读，读不到只是失败、不会崩），找到占位后原地写，长度不超过占位，没写满补结束符；
  - 每次写之前核对内容还是占位或上次写的。
- dark_sell 的确认框预计件数就是这个办法，游戏里实测扫一遍约 5 秒，能找到。
- **注意**：DLL 自己手里的占位副本用完要清零，免得以后再扫时把释放掉的副本当成游戏的文字。

### 6.5 容量估算

| 项 | 估算 |
|---|---|
| 参数表行数 | 每张 ≤ 65535 行。武器容器 2000 行 + 每件 4 行效果 = 8000 行效果，没问题 |
| 武器编号 | 必须 < 0x10000000，查表按 ÷ 100 × 100。不做质变的话每个容器占 100 个编号就够，2000 个只要 20 万个编号。要支持质变就得每个占 1 万，空段有限：26500 万~26843 万只放得下 343 个，要另找空段 |
| 文字 | 每个容器 3 段占位。名字 160 字、简介 240 字、说明 1200 字，2000 件约 320 万字（每种语言约 6.4 MB），可以接受；正式版可按实际需要缩短 |

### 6.6 已有 / 要新做的能力

| 能力 | 状态 |
|---|---|
| 运行时改参数行 | 底层库已有，已在用 |
| 从背包移除物品 | dark_sell 已有 |
| 物品菜单加选项 | dark_lock 已有 |
| 按角色存记录、两个游戏版本的地址表 | 已有 |

| 往背包加指定物品 | 要逆向，两个版本各一次 |

### 6.7 风险

- **记录文件丢失**：新装备会变回空白容器。这和现在配方文件丢失是同一种风险，现有的配方历史备份可以照搬。
- **容器用满**：同一角色持有太多就不能再生成，需要提示玩家卖掉一些。
- **联机**：别人看到的是空白容器的数值；纯离线没有影响。
- **老装备**：现有固定编号的装备保持不动，和容器装备共存，老存档不用迁移。
- **关掉功能前**：玩家手里的容器要先处理掉，否则编号不存在。现有 `leftover_test_weapons` 的做法可以借鉴。

### 6.8 更彻底、但不先做的方案

让 DLL 接管游戏「按编号查装备参数」的函数，编号本身就当随机种子（武器编号空间够放两百多万个），装备数据完全存在存档里，没有容器上限也不需要记录文件。

不先做的原因：游戏里读装备参数的地方很多（面板、攻击计算、商店、强化、联机），漏掉一处就会显示错误或崩溃，逆向工作量和风险都大得多。

- **为什么基数本身改不了**：原版法杖之间的差别全来自补正值（correctMagic，比如辉石杖 85 / 卡利亚权杖 96 / 卢瑟特的辉石杖 110）、
  补正曲线（correctType_Magic）和强化的补正倍率（correctMagicRate，+0 = 1.0，满级 3.0）；所有法杖 attackBaseMagic 都是 0，
  强化的 magicAtkRate（满级 2.45）也不进法术补正（算进去卢瑟特的辉石杖 +10 就是 1013，不算是 414），所以 100 是写死的。
  第一版做成了拿着法器时挂「法术伤害 × B / 100」的效果（面板不显示），当天改成下面的做法。
- **现在的做法：补正值 × 倍率**。gear.rs `build_row`：能施法的本体（affixes.txt 的 `wcast <本体> <魔法> <祷告>`，按原版 enableMagic / enableMiracle，
  62 种，含卡利亚魔法剑 2530000）的五项补正值 × 倍率 ÷ 100 写进参数行；配方里存的不乘，重铸、以后的超限都照配方算。
  面板上的补正、法术补正直接显示乘过的数；工坊的「当前补正」读的是参数行，「重铸范围」预览（workshop.rs reforge_preview）也乘上了。
  装备说明里不另写（用户：「应该直接能在补正上体现出来」）。
- **倍率**：gear.rs `cast_base` 在稀有度区间（`cbase <r> <下> <上>`，百分数，settings `catalyst_base`）里抽截断正态（同防具减伤：均值 = 中点，
  区间 = ±2σ，抽到外面重抽），按记录（容器序号、档、本体）定，同一件每次一样、重铸不变。用户同日放宽成普通、稀有 ±30，史诗、传说 ±50：
  普通 70~130、稀有 90~150、史诗 110~210、传说 150~250（普通、稀有可能低于原版；法球也照乘，低于 1 也乘）。
- **和「基数」的差别**：补正值 × m 只放大加成那部分，100 那部分不变。传说法杖毕业时（补正约 655）基数做法是 1310、这样是 1210，约少 8%；属性越低差得越多。
- **副作用**：跟着法术补正走的都变强——治疗类祷告的回复量、附魔类法术；生成法器拿来敲人的物理伤害也跟着补正涨（法器基础攻击很低，影响不大）。
- **法球**：write_row 时把倍率记进 `CAST`（编号 → 倍率），`cast_of` 查；dark_core `spellbase.rs` 每 6 帧看左右手拿着的生成法器，
  取最高的倍率 ÷ 100 给 `orb_factor()`，积木规则 `burst_spell=1`（迸发、星群）的固定伤害乘它。
- **词条**（extract_affixes.py，重新提取了词条库）：
  - 血涌 20 / 30 / 40 / 50％，只有魔法、祷告两行（战技那行去掉）；流派关键词加了「魔法与祷告」，还算法术流派。
  - 背水每失去 10％ 血量 +2 / 3 / 4 / 6％，第 n 档 = 1 + n·v（以前 (1 + v)^n），传说血量 10％ 以下 ×1.54。
  - 涌流每颗 8 / 12 / 16 / 20％；有 n 颗时 n 行同时挂，第 n 行取 (1 + n·v) / (1 + (n-1)·v)，乘起来正好 1 + n·v（传说 3 颗 ×1.6、4 颗 ×1.8）。
- 生成法器的补正表（42300）五项属性都能加成五种伤害，所以法器身上所有有补正的属性都加成法术（原版法杖只认智力、圣印记只认信仰）。

### 8.25 原版类型数值词条同稀有度叠加（2026-11-03，等游戏内看）

用户：「原版类型数值词条改为都能任意稀有度都能叠加」，又「触发型的先不处理」。

- 原因：原包那类词条每个稀有度只有一个效果编号，两件同稀有度的装备挂的是同一个效果，游戏里只算一次（不同稀有度是不同编号，本来就叠）。
- 做法沿用 2026-11-01 属性加点的那套：`rr/affixes.py attr_copies` 给效果建 8 份数值一样、编号不同的副本（7300000~7301471），
  runtime.txt 的 `attrdup` 行；dark_core `attrstack.rs` 每 15 帧数防具 4 件 + 护符 5 格里每个效果出现几次，第 2 件起补挂副本。副本和原效果相乘（两件传说重击 = ×1.25²）。
- 范围：原包词条里效果行不引用别的效果的 46 种（184 个效果），含属性加点、圣杯（dr_flask）。
- 不做：附近触发、命中时触发（机制类）；新词条（积木引擎 / 玩家脚本 / dark_core 只认最高稀有度）；
  触发型（效果行会再挂别的效果，按 `SP_REF_FIELDS` 认）：蛋白石盾、悲伤、远征、黄金蹲姿、臭气嘲讽（翔空箭 2026-11-05 放开，`STACK_CHAIN_KEYS` 连周期挂的射程行一起复制）；狂怒突刺（致命一击后才生效，说明写着同稀有度仅生效一次）。
- 说明（用户：「给不能叠加的都加上说明」「分为同稀有度不能叠加和取最高稀有度」）：extract_affixes.py `stack_notes` 给说明加最后一行——新词条（积木引擎 / 玩家脚本 / dark_core，只认最高稀有度）「同名词条取最高稀有度」，武器特效「同名特效取最高稀有度（双持时）」；原生效果、只是同稀有度同一个效果的（附近触发、触发型原包词条、狂怒突刺、饮血）「同稀有度不叠加」，原包的「同稀有度仅生效一次」「不叠加」统一换成这句；命中时触发、召唤类附近触发（风爆、风盾、天矛、风矛「同名效果不叠加」）照原句。能叠的数值词条不写。
