# 崩溃风险审查（2026-11-19）

范围：dev 下全部 DLL 源码（dark_core / dark_ui / dark_dev / dark_lock / dark_sell / dark_slot / dark_wings）、启动器生成 YAFSML 配置的部分（launcher\dfl）、重随数据管线（launcher\reroll），以及和 YAFSML 0.10.4、Seamless Co-op 2.0.2、ErdTools、ertransmogrify、souls_vision 的交互。
方法：只读，没改代码、没编译、没进游戏。dark_core 的几处代码补丁用 capstone 在本机 exe 上逐字节核对；四份 regulation 用只读脚本核对。
已接受的已知崩溃（退出 DL_PANIC、mimalloc YAFSML+0x3431c、Scaleform 0x11a6b79 / 0x11b182a）不重复列。

「核实」一栏：**已核实** = 我对照源码或数据亲自确认；**子任务实测** = 审查子任务跑脚本测出、我没复跑；**推断** = 有代码依据但后果没验证。

## 一、一旦触发就崩（触发条件本身有条件）

### 1. dark_ui：DX12 管线重建后 `initialize` 再跑一次 → XInput 无限递归 / 贴图编号越界
- 位置：`dark_ui\src\lib.rs:466`（`hooks::install()` 没防重入）、`dark_ui\src\hooks.rs:262`（先把原函数地址写进 XGET 再挂钩）、`hooks.rs:39-46`（挂钩失败时不改 slot）。
- 过程：
  - 第二次挂钩 `MH_CreateHook` 返回「已经挂过」，XGET 停在已被挂钩的 XInputGetState 入口。之后调 `xinput_get_state` 就跳回自己，栈溢出（0xC00000FD）。游戏每帧都调 XInputGetState，所以重建后立刻崩。
  - `lib.rs:474` 只调 `self.tex.start()`，图标缓存里的旧 TextureId 不清；下次开工坊时 hudhook `backend\dx12.rs:321-322` 越界 panic，这里在 Present 钩子里，直接 abort。
- 触发：hudhook 重置管线。会重置的情况包括：交换链格式或缓冲数变了（切 HDR 很可能算），同一窗口新建交换链（帧生成 / 超分类 mod），字体图集建不出来（之后每帧都重跑 `initialize`）。
- 核实：**已核实**（代码路径）。本机 17 份 dark_ui.log 都只有一次「初始化开始」，开发机没遇到过。
- 怎么认：dark_ui.log 出现第二次「初始化开始」，或者 hudhook 的「Resetting DX12 pipeline」警告。
- 修法：`hooks::install()` 用 OnceLock 只装一次；`hook_xinput` 只在 XGET 为 0 时写；`initialize` 开头重置 `self.tex`；字体字节缓存起来，不要每次重新 leak。

### 2. hudhook 收到 UTF-16 代理字符的 WM_CHAR → unwrap 失败 → abort
- 位置：hudhook 0.9.3 `renderer\input.rs:339`：`char::from_u32(wparam).unwrap()`，在 Present 里处理排队的消息时执行。
- 触发：输入 emoji 或扩展区生僻字（Win+. 表情面板；玩家在 YAFSML自定义.ini 打开 `enable_ime=1` 后用输入法）。dark_ui 只在自己的搜索框打字时才过滤（`hooks.rs:107`、`:119-126`）。
- 核实：**已核实**。dark_dev 同样有，但它不进发布包。
- 修法：第一次 `before_render` 就装上子类窗口过程，一直丢弃 0xD800–0xDFFF 的 WM_CHAR；或者 vendor hudhook 改成 `if let Some(c)`。

### 3. FrameBegin 回调开头三个调用没包 `guarded`
- 位置：`dark_core\src\lib.rs:255-257`：`perf::frame`、`prof::frame`、`chrs::refresh_players`。
- 任务回调是 vendored `shared\src\task.rs:103` 的 `extern "C" fn execute`，里面没有 catch_unwind，这三个一旦 panic 游戏就直接退出。现在看不出它们会 panic，属于加固项。dark_sell 的 `poll_sell` 同理。
- 核实：**已核实**。
- 修法：一起包进 `guarded`。

## 二、数据侧：存档里的物品引用了不存在的参数行（读档、开背包时很可能崩）

### 4. 生成装备的编号按顺序分配，各世界不同，存档却共用
- 实测开局武器段（230000000 起）：敌人随机 28 行、死亡以上 29 行、无敌人随机 30 行；230280000 / 230290000 只在部分世界存在。编号和本体的对应关系也会跟着前面职业的武器数平移。
- 原因：`launcher\reroll\rr\startgear.py:222-225` 按 `len(ids[0])` 顺序编号；武器表来自随机器的 CharaInitParam，每个世界不同。单机存档 ER0000.rng 三个世界共用。
- 同类代码（子任务列出）：支线装备 `rr\unidentified.py:786/795`、商人小极品 `rr\shops.py:494`、英雄防具 `rr\shops.py:373`、特殊货币传说武器 `rr\remembrance.py:135-137`（只在开物品随机时建）、专属战技战灰 `rr\skillgems.py:250-253`（动作包做不成时 145 行里有 89 行不建）。
- 触发：在无敌人随机世界建的角色拿着 230290000 去敌人随机世界读档；或一键重随敌人后开局武器数变了。dark_core 读档时只能改写已有的行，补不出缺的行。
- 核实：**已核实**（重跑脚本，三份 regulation 行数如上）。缺行会不会崩没有实测，经验上装备着缺行的武器读档会崩。
- 修法：每个编号段整段建满占位行（照一件原版复制），不管用没用；战灰行总是建，做不成只是不上架；容器个数只增不减。

### 5. 随机器写进开局职业的武器编号本来就不存在，管线跳过后原样留着
- 敌人随机世界：CharaInitParam 3002（勇者）、3006（忏悔者）、3104/3105/3112/3113 的右手武器 = 4401055 / 4407062；死亡以上：3004（占星）、3108/3109 的右手副武器 = 5040。EquipParamWeapon 里都没有。
- 位置：`rr\startgear.py:140-142` 遇到不存在的就 `continue`，不报告也不修。
- 触发：选这几个职业建新角色（创建画面预览、第一次进游戏）。
- 核实：**已核实**（重跑脚本）。会不会崩没实测。
- 修法：无效编号换成同职业的生成武器或原版武器（或写 -1），并写进重随报告。

### 6. scripts 构建失败时沿用旧包，旧包里整张的 MSB 引用的 NpcParam 副本号已经移位
- 位置：`launcher\reroll\scripts.py:194-196`；副本号按 `sorted(need)` 找空号（`rr\stage3.py:1137-1148`），随机器输出一变就整体移位。
- 触发：读 m11_00、m11_05、m11_10、m14_00、m60_42_40（高难度世界更多）时，敌人引用缺行或错行。
- 核实：子任务读代码，**推断**。
- 修法：沿用签名里加来源地图的 hash；来源变了就不沿用，或删掉旧包的 `map\`、`event\m*`。

### 7. stage3 提前返回时，上一次的 reroll_maps 照样挂载
- 位置：`rr\stage3.py:1062-1063`、`1090-1091` 直接 return，不清旧地图；`dfl\launch.py:936` 照常挂 DR_RerollMaps。
- 核实：子任务读代码，**推断**。
- 修法：这两处改成报错（重随失败启动器不会启动游戏），或者清掉旧地图。

### 8. MSB 缓存写入不原子、读取不校验
- 位置：`sc\extragrace.py:104`、`sc\arena.py:133`、`sc\bossarena.py:263`、`sc\lostarena.py:156` 都是直接 `open(...,'wb').write`，读的时候文件存在就用。写到一半被打断，半截文件会被一直复用。
- 修法：tmp + `os.replace`；读时检查 DCX 能解开、开头是 `MSB `。

## 三、联机（Seamless Co-op）

### 9. 赠送能把穿着的防具 / 护符送走
- 位置：`dark_core\src\gear\gift.rs:140-141`。`inv_slots` 返回的是普通格序号（不含 `key_cap`），而 `equipment_item_idx_list` 存的是 `key_cap + 序号`，所以 `eq_idx.contains(&slot)` 永远查不中。另一条 `eq_ids` 只含 6 把武器，防具和护符漏掉了。`recycle_list`（gear.rs:4163）写的是对的。
- 后果：对方收下后 `remove_slot` 用游戏的移除函数整格删掉，ChrAsm 还穿着它，装备表指向空格，之后捡到的东西填进这一格。另外 GOK 分支（gift.rs:208-211）不重查装备状态，等回话的 60 秒里装上的武器也会被移走。
- 核实：**已核实**（bug 确定；会不会崩没进游戏验证）。
- 修法：改成 `key_cap + slot`，并照 dark_sell 的 `equipped_ids` 查防具、护符、誓约槽；GOK 时重查，装备着就不移。

### 10. 收到强化等级超过 +5 的赠送武器，换成新强化类型后查不到强化行
- 依据：`rr\upgrade.py:174` 只给新强化类型建 0~rmax 级；`build_row`（gear.rs:2378）只有 `over_max` 里有的格子才保留原版类型；`gift.rs:163-174` 收到的 `lv` 最高 25。开局装备不在记录里时也可能走到这一步。
- 核实：子任务读代码，**推断**。
- 修法：upgrade.py 给每个新类型补 rmax+1 到 25 级（复制 +rmax 那行）；`receive()` 在 `lv > rmax` 时先把格子放进 `over_max`。

### 11. 联机通道不收消息时还每秒发 HELLO，可能堵住和 Seamless 共用的 Steam 连接
- 位置：`dark_core\src\link.rs:656-695`：`link` 为 None 时整帧不收；`link.rs:313-317`：没连上时每秒一条带档案的 HELLO（Reliable），永不停。
- 依据：ersc.dll 也用 SteamNetworkingMessages002；同一个人的所有频道共用一条连接，接收缓冲超限会丢包。
- 触发：队伍里有人一直不读我们的频道（没跑本整合包、dark_core 没起来、名单一直没就绪）。
- 后果：大约 15–20 分钟后可能出现断线、同步卡死；不一定崩。
- 核实：代码**已核实**，后果**推断**。
- 修法：ersc 加载着就每帧把本频道收掉（不在会话时收了直接丢）；HELLO 退避，几分钟没回就停，名单变了再开始。

### 12. 联机核对码和兼容档案不含玩家自己的 mod
- 位置：`launcher\reroll\coopfp.py:23-37`、`launcher\dfl\coop.py:456-483` 没算 mods\、[mod]、[mod_after]。[mod_after] 里的 regulation / msb / emevd 会盖过整合包。
- 后果：核对码一样，两边实际数据不同，同步时可能掉线或崩。
- 修法：档案里加实际挂载的玩家 mod（名字 + 文件清单 hash）；[mod_after] 里有 regulation / map / event 时拒绝联机启动。

## 四、加载链 / YAFSML / 启动器

### 13. YAFSML自定义.ini 的 [dll] 绕过所有 DLL 安全检查，也不去重
- 位置：`launcher\dfl\usermods.py:248-277` 只查文件在不在、是不是 ersc.dll；`test_user_dll_safe` 只在自动扫描（`launch.py:212-216`）里调。
- 触发：
  - 玩家照法魂的配置写一行 ErdTools：那份 ini 不会被改写，`persistent_lantern=1`（已知 ErdTools+0x13D43 崩溃）、`save_extension=cnv`（读写法魂存档）都会生效。
  - 双显卡的 souls_vision 开关也被绕过。
  - 自动扫描按键名去重，不按文件：`dll\dark_core\` 里多一份「dark_core - 副本.dll」会加载两份 dark_core。
- 核实：**已核实**。
- 修法：[dll] 条目也走 `test_user_dll_safe`；按完整路径和文件名（不分大小写）去重，提示文件名带「副本」/「- Copy」/「(1)」的 DLL。

### 14. 启动头几秒多个 MinHook 同时冻结线程，souls_vision 没有错开
- 依据：MinHook 每次启用钩子都会 SuspendThread 进程里其他所有线程。dark_ui 加载后马上装 DX12 钩子，约 4 秒时再逐个启用 5 个输入钩子（`dark_ui\src\hooks.rs:39-47`）；同一时间段 ErdTools、ertransmogrify、souls_vision 也在装。dark_ui 的 HookLock 只和 dark_dev 排队。启动器生成的 `user_souls_vision` 行不带 delay（YAFSML 自带示例写的是 `delay,2000`）。
- 后果：极小概率启动卡死（没有崩溃记录），或抄到写了一半的跳板。
- 核实：**推断**。
- 修法：souls_vision 加 `|delay,3000`；dark_ui 输入钩子改成 queue 后一次 `MH_ApplyQueued`。

### 15. 两个启动器同时启动会互相踩
- 依据：`启动.bat` 直接 `start pythonw`，没有进程级互斥；`launch.py:996` 只在生成前查一次游戏在不在跑；`start_yaf_game`（`launch.py:631-633`）看到游戏在跑就直接 kill。
- 后果：两套重随同时写 regulation / scripts / dark_core 定义文件，留下半截文件；或者把刚启动的游戏杀掉，赶上写存档会坏档。
- 修法：命名 mutex（拿不到就把已有窗口提到前台）；`start_yaf_game` 遇到游戏在跑就报错退出，不要 kill。

### 16. 启动前不检查 Game\ 顶层的代理 DLL
- 只有崩溃诊断（`diag.py:505`）才列出它们。本机 Game\ 下就有 Elden Mod Loader 留下的 `mod_loader_config.ini` 和 `mods\`。玩家留着 dinput8.dll / dxgi.dll 时会在同一进程再加载一套 DLL（再来一份 ersc 或 ErdTools 必出事）。
- 修法：启动前扫常见代理文件名并提示；联机时直接拒绝。

### 17. 游戏脚本包合并失败时，dark_lock 照样加「锁定 / 送给」选项
- `launch.py:418-421` 合并失败照常启动；文字 4190–4196 只由 `sc\lock.py` 写进 out\scripts；`dark_lock\src\lib.rs:582-619` 不管文字在不在都加选项，msghook 对空指针原样返回。游戏建选项时能不能容忍空文字，**没验证**。
- 修法：合并失败时写一个标记文件，dark_lock 看到就不加。

## 六、核对过、认为安全的

- **dark_core 代码补丁**（capstone 在本机 exe 上核对）：
  - castpanel：被改的「mov eax,0x13」分支只有两个入口（`ja` 和跳表第 1 项），都在 rcx = 武器参数行的那一段里，空指针分支也安全。
  - scaling：补正分支进入时 rcx == rbx（输出缓冲），我们的 `call rax` 和原来的调用位置相同，"-" 分支跳回的地方不依赖被改的寄存器。
  - msghook：跳板里 `jae` 改长跳的偏移正确；对 ertransmogrify / ersc 先挂的 E9 能接链；返回给游戏的缓冲都不释放；detour 里有 catch_unwind。
  - pickup：8 字节对齐原子写，接链逻辑同上。
- **dark_slot**：全部核对通过才改；ersc 先挂了槽位函数头时只改 .data 函数表；181 处单字节写是原子的。
- **DllMain**：7 个 DLL 都返回 1，loader lock 里只开线程、写日志（dark_lock 在 DllMain 里装钩子，只做分配、改保护、读字节）。
- **跨 DLL 接口**（dr_ws_* / dr_gift_* / dr_msg_confirm / dr_prof_*）：签名一致，先比 API 版本，长度都校验并拷贝。
- **角色指针**：rules / curses / nightmare / hpunify / plague / foefx / speed / 斗技场 / 骨灰跨帧存的地址，解引用前都和当帧 `live!` 核对；距离列表都走 `around!`。
- **写进游戏的数值**：架势、血量下限、朝向四元数、减速倍数都有夹限和 NaN 保护。
- **联机通道解析**：只用 Option / Result，只收名单里的人，各队列有上限，整个 tick 在 catch_unwind 里。
- **参数写出**：总是按 ID 排序；`add_row` 查重和行长；regulation 写完读回校验；四份输出相对原版 + 随机器没有新增悬空引用（Boss 模组带进来的 17 个除外，原版本身就有约 500 个）。
- **EMEVD / ESD**：400 个随机器 emevd 读出再写回逐字节一致；没有向后 goto。
